# Free-tool acquisition playbook

## Choose the job and the distribution together

A useful tool can still be a poor acquisition asset. Check three links: the people requesting the result match buyers; the result exposes a problem the paid product can fix; and a named placement can get the first users to it. Search demand, ranking difficulty, and CPC must come from current research, not guessed numbers.

| Mechanism | Useful output | Credible paid next job | Main trap |
| --- | --- | --- | --- |
| Validator | A reproducible error report | Fix or continuously prevent the error | Claiming a diagnosis the tool cannot establish |
| Converter | A working transformed file | Repeated imports, sync, scale | One-off users with no ongoing need |
| Calculator | A decision with visible assumptions | Execute or monitor the decision | Precise-looking output from invented inputs |
| Generator | A usable artifact | Maintain, collaborate, deploy | Generic output available everywhere |
| Reference dataset | Clean, dated information | Freshness or workflow integration | Maintenance dominates acquisition value |

## Before building

Find five target users with the job, using actual Reach list entries. Five is a proposed learning sample, not a universal threshold. Offer to produce the result manually. Observe whether they use it, ask for another one, and want the paid next step. Record a rejection as useful evidence. A polished demo shown to friends does not answer these questions.

Draft an input/output specimen, failure state, and result page before a build brief. Where inputs may contain private data, define what is needed, whether processing can be local, and deletion expectations. For URL-based graders, include an engineering review of arbitrary URL fetching and compute limits in the handoff; this skill does not implement the service.

## Worked planning example: CSV importer

Hypothetical, not a customer claim. A paid import service handles recurring large files. A free CSV preflight checks headers and inconsistent rows locally and returns a repaired sample plus error counts. The next job is a full import preview in the paid product. The first placement is one community thread where a user already asked about malformed imports, subject to its rules.

Pilot proposal: manually review five consenting users' synthetic/redacted examples in one week; continue if at least three use the result and two request a full import trial. Otherwise inspect whether the problem, audience, or paid bridge failed. These are chosen thresholds, not benchmarks. No build until demand survives that test.

## Contribution model

Use a fixed observation horizon. Let C = build + distribution + maintenance + variable usage cost. Let A = qualified users activated into the main product, and P = customers acquired within the horizon. Tool cost per activated user = C/A; cost per customer = C/P. Undefined denominators mean no measured acquisition yet.

Hypothetical: a $300 pilot and 15 activated users cost $20 per activation. If three become customers, acquisition cost is $100, not $20. Compare with contribution from those customers over the same horizon. Do not compare gross lifetime revenue to one week's cash spend. Include founder hours separately even when the cash budget is zero.

## Result page and events

Deliver a useful result before optional capture where feasible. A save/export, monitoring alert, or further diagnostic can justify an email request; disclose exactly what follows. Do not make every use require signup by habit.

Events: qualified landing visit → started → completed useful result → clicked relevant next job → product first value → returned/purchased. Store source placement and tool version. Count unique users, exclude internal tests, and avoid sending raw private inputs to analytics. A completion rate without audience quality can reward the wrong tool.

## Cases and limits

[HubSpot's announcement](https://www.hubspot.com/blog/bid/1387/website-grader-passes-10-000-mark) reports over 10,000 websites evaluated in about three months; it does not give customer conversion. [Unsplash's cofounder](https://unsplash.com/blog/hello-unsplash-inc/) describes a free resource becoming Crew's leading customer source and later an independent company. The adaptation is a small useful output; the warning is that a side project can consume its own team.

## Stop or revise

High completions but no paid next step: test the bridge and buyer match. Many visits but no useful output: fix the tool. No qualified visitors: test distribution before rebuilding it. Unexpected API costs: enforce the agreed cap. A successful free product with no paid relevance is a separate business decision, not automatic GTM success.
